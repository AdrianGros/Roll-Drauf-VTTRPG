# B07 production vision ID repair

Status: Discover and Apply complete for this confirmed schema defect. Retention permanent.
Input: normal DM session journey on the B07 image, source `1f469309d`.

Observed: POST vision/lights returns HTTP 500: PostgreSQL rejects a null `id`.
Read-only inventory finds `scene_lights`, `scene_walls`, `fog_of_war_state` each
has an integer primary key without an identity, sequence or default; all three
are empty. The original M71 SQL uses `INTEGER PRIMARY KEY`, which auto-generates
IDs in SQLite but not PostgreSQL. Models and ordinary PostgreSQL ORM-created
schemas expect generated IDs. No permission or geometry algorithm defect is
needed to explain this failure. Medium delivery blocker: B07 is deployed but
must remain incomplete until production creates geometry and fog successfully.

Design: a bounded, explicit PostgreSQL migration for only these three ID columns.
Lock the three tables in a stable order, with short lock/statement timeouts. Add
`GENERATED BY DEFAULT AS IDENTITY` only where no generator/default exists,
starting above the current maximum (at least 1). Preserve existing valid serial
or identity generators; reject unexpected defaults/types/keys. Re-running must
not reset sequences. Transactional DDL must preserve every existing row.
No other table, column, constraint or data migration is authorized by this repair.

Verify against an isolated instance of the already available production PostgreSQL
image: reproduce failed implicit inserts, preserve seeded rows, generate IDs
above existing maxima, repeat without resetting, preserve existing serial IDs,
and fail/roll back on unexpected schema. SQLite tests remain useful for domain
behavior but cannot validate this dialect-specific defect.

Deploy handoff: commit/push the migration and proofs; take and validate a fresh
database dump; run the transaction against actual production; record before/after
metadata. Keep the current B07 application image. Repeat normal DM and Player
live journeys, including fog effect and denial checks, then remove own fixtures.
The app rollback remains compatible with generated IDs; retain this additive
repair on app rollback. Database restore is a separate recovery operation, not
an automatic app rollback. Do not drop a live generator after new rows exist.

Acceptance: actual DM light/wall insert/edit/reload/delete succeeds, Player fog
is created and changes with lighting/walls; no permission relaxation; unrelated
service identities unchanged. Record source/image and migration commit separately.

Reference: PostgreSQL [ALTER TABLE](https://www.postgresql.org/docs/16/sql-altertable.html)
documents identity generation for subsequent inserts and transactional table DDL.
