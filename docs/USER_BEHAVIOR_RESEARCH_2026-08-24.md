# User-behavior research brief — GUI friction audit for Roll Drauf VTT

**Date:** 2026-08-24
**Scope:** observable visual and interaction friction in the login → dashboard → play journey.
**Status:** research and test-design guidance only; no application code was changed for this note.

## Executive synthesis

The strict robot should test whether a player can perceive the intended next action, acquire it accurately, understand the result, and recover from mistakes. It should not claim to measure human attention from screenshots alone: visual-attention claims require eye-tracking or real-user observation. Playwright can measure defensible behavioral proxies—first meaningful action, retries, backtracks, focus movement, geometry, visible state changes, and task latency.

The evidence does not support simplistic rules such as “make the largest element the primary action” or “limit every screen to seven choices.” Web-page entry points are influenced by position and distinctiveness as well as size, and choice overload depends on task difficulty, choice-set complexity, uncertainty, and goals. The operational rule for this VTT is therefore: make the intended task path visually distinct, keep competing actions subordinate, and validate the result with task telemetry rather than aesthetic judgment alone ([Still, 2018](https://doi.org/10.1016/j.chb.2018.03.014); [Chernev et al., 2015](https://doi.org/10.1016/j.jcps.2014.08.002)).

## Evidence translated into robot heuristics

| Friction area | Primary evidence | Operational heuristic for the strict journey |
|---|---|---|
| Visual hierarchy and attention | In two eye-tracking studies, visual hierarchy predictions based mainly on size performed poorly; position and distinctiveness better predicted earlier engagement. The UEyes CHI study provides a UI-specific eye-tracking dataset of 1,980 screenshots from 62 participants and reports UI-type differences in saliency ([Still, 2018](https://doi.org/10.1016/j.chb.2018.03.014); [UEyes, CHI 2023](https://doi.org/10.1145/3544548.3581096)). | At each checkpoint declare one primary task and its expected target. Record whether it is visible, labeled, enabled, inside the intended region, and the first meaningful control activated. Flag competing visible CTAs at the same visual weight, duplicate active navigation, unexpected overlays, and primary actions below the fold when the task requires them immediately. Treat “time to first action” as a proxy, not a gaze measure. |
| Target acquisition and interaction errors | Fitts’ original experiment models movement time as a function of distance and target width ([Fitts, 1954](https://doi.org/10.1037/h0055392)). WCAG 2.2 requires a 24×24 CSS-pixel minimum pointer target with exceptions and defines 44×44 as the enhanced target-size criterion ([WCAG 2.5.8](https://www.w3.org/WAI/WCAG22/Understanding/target-size-minimum.html); [WCAG 2.5.5](https://www.w3.org/WAI/WCAG22/Understanding/target-size-enhanced.html)). | Measure every critical button, link, tab, close control, and touch token with `getBoundingClientRect()`. Gate below 24×24; use the product’s stronger 44×44 touch rule for primary phone actions. Also measure target spacing, clipping, overlap, and whether the click point is intercepted by another layer. Count failed clicks, repeated clicks, accidental adjacent activations, and drag-cancellation failures. |
| Login and form usability | A controlled eye-tracking experiment with 65 participants found that improved web forms produced faster completion, fewer submission trials, fewer eye movements, and higher satisfaction ([Seckler et al., Google Research/CHI 2014](https://research.google/pubs/designing-usable-web-forms-empirical-evaluation-of-web-form-improvement-guidelines/)). WCAG requires labels/instructions, identification of input errors, useful correction suggestions where known, and an accessible authentication path that does not unnecessarily require memory, transcription, or blocked paste ([WCAG 3.3.2](https://www.w3.org/WAI/WCAG22/Understanding/labels-or-instructions.html); [WCAG 3.3.1](https://www.w3.org/WAI/WCAG22/Understanding/error-identification.html); [WCAG 3.3.3](https://www.w3.org/WAI/WCAG22/Understanding/error-suggestion.html); [WCAG 3.3.8](https://www.w3.org/WAI/WCAG22/Understanding/accessible-authentication-minimum.html)). | Run the real logged-out form, not an API-authenticated shortcut. Verify accessible names, autocomplete/input purpose, paste, keyboard order, preserved values, one clear submit action, and no duplicate visible forms. Execute an invalid submit and a valid submit. Record submission count, correction count, focus destination, error-to-field association, and time to recover. |
| Feedback and error recovery | Two empirical web-form studies found that showing errors immediately during completion could be ignored, while presenting errors after the form was completed performed better in those tasks ([Bargas-Avila et al., 2007](https://doi.org/10.1016/j.intcom.2007.01.003)). This is task-specific evidence, not a universal ban on inline validation. W3C requires the erroneous item and error to be identified in text, and status changes must be programmatically determinable without moving focus unnecessarily ([WCAG 3.3.1](https://www.w3.org/WAI/WCAG22/Understanding/error-identification.html); [WCAG 4.1.3](https://www.w3.org/WAI/WCAG21/Understanding/status-messages)). | Test feedback as a state transition: action → visible status/error → recoverable next action. Require a message that names the problem, remains readable at the tested zoom, is associated with the field or status region, and does not erase valid input. Measure feedback latency, whether focus is sensible, whether the user can retry without restarting, and whether success is visually unambiguous. |
| Cognitive load and choice | Sweller’s experiments established cognitive load as a constraint on problem solving ([Sweller, 1988](https://doi.org/10.1207/s15516709cog1202_4)). A 2022 online-booking study found choice-overload effects varied with choice size, information amount, and presentation; a meta-analysis identifies choice complexity, task difficulty, preference uncertainty, and decision goals as moderators ([Guo & Li, 2022](https://doi.org/10.1080/10548408.2022.2044970); [Chernev et al., 2015](https://doi.org/10.1016/j.jcps.2014.08.002)). | Do not enforce an arbitrary option cap. For each task record the number of simultaneously visible primary choices, time to first commitment, reversals/backtracks, dead-end navigations, and whether a choice requires remembering information from another surface. Flag screens where secondary actions visually compete with the declared next step or where the user must reopen panels to compare required information. |
| Accessibility, zoom, and responsive behavior | WCAG 2.2 requires meaningful structure, visible keyboard focus, 200% text resizing, reflow at a 320 CSS-pixel equivalent width without loss of information/functionality (except genuinely two-dimensional content), and focus not being entirely obscured ([WCAG 1.3.2](https://www.w3.org/WAI/WCAG22/Understanding/meaningful-sequence.html); [WCAG 2.4.7](https://www.w3.org/WAI/WCAG22/Understanding/focus-visible.html); [WCAG 1.4.4](https://www.w3.org/WAI/WCAG22/Understanding/resize-text.html); [WCAG 1.4.10](https://www.w3.org/WAI/WCAG22/Understanding/reflow.html); [WCAG 2.4.11](https://www.w3.org/WAI/WCAG22/Understanding/focus-not-obscured-minimum.html)). | Repeat login and dashboard checkpoints at narrow desktop, 320-CSS-pixel-equivalent reflow, 200% text zoom, phone portrait, and phone landscape. Assert no non-exempt horizontal overflow, clipped text, hidden focus, keyboard trap, or two-dimensional scrolling outside the intentional map/table workspace. Keep surrounding navigation, headings, controls, and status surfaces in the one-direction reflow contract. |

## Strict GUI journey to implement next

The journey should run with a declared target, role, browser, viewport, DPR, locale, color scheme, reduced-motion setting, and commit identifier. Missing or skipped checkpoints are `blocked`/`inconclusive`, not green.

1. **Login initial:** start logged out; assert route, language, title, one primary heading, one visible form, labels, password-manager-compatible inputs, visible focus, target geometry, and a screenshot.
2. **Login recovery:** submit empty/invalid data; assert the form remains usable, the offending field is identified in text, the message is programmatically associated, focus is recoverable, valid values are preserved, and a screenshot is captured after the error settles.
3. **Login success:** submit valid credentials exactly once; capture the loading/transition state; assert redirect to the expected dashboard and record redirect plus settled-state latency.
4. **Dashboard settled:** assert one visible primary surface, one current navigation state, identity/session state, one obvious next action, no stale loading curtain or duplicate scene, and a screenshot plus layout metrics.
5. **Keyboard path:** tab through the primary controls; verify focus visibility and focus order, activate the next action without a pointer, and verify that focus is not covered by fixed chrome or sheets.
6. **Responsive/zoom matrix:** repeat the visible login/dashboard contract at the device profiles above. Use the map/table as a documented two-dimensional exception only where spatial interaction is the product’s meaning.
7. **Role journey:** repeat the dashboard-to-play handoff for DM and player roles, then test the first role-specific action. Role setup may be API-assisted, but the visible handoff and action must use the UI.

## Metrics and evidence contract

| Metric | Definition / collection | Interpretation |
|---|---|---|
| Task completion | Ordered checkpoint pass/fail with required evidence present | Primary outcome; never infer success from DOM existence alone. |
| Action latency | `performance.mark()` around submit, navigation, panel open, and first meaningful action; supplement with `PerformanceNavigationTiming` | Compare to an environment baseline; do not turn an arbitrary sleep into a usability budget. W3C defines navigation timing fields such as `domInteractive`, `domContentLoadedEventEnd`, and `loadEventEnd` ([Navigation Timing 2](https://www.w3.org/TR/navigation-timing-2/); [User Timing](https://www.w3.org/TR/user-timing/)). |
| Error/recovery rate | Invalid submits, repeated submits, field corrections, backtracks, dead ends, and failed/ intercepted pointer actions | Direct automated proxies for interaction friction; report per checkpoint and role. |
| Target geometry | Width/height, center-to-center spacing, viewport containment, ancestor clipping, overlap, and hit-test result | Hard gate critical controls at 24×24; apply 44×44 as the VTT touch target standard. |
| Feedback quality | Time to status/error, visible text, field association, accessible name/description, focus destination, and retry success | A response that exists in the DOM but is not visible, readable, or announced is not usable feedback. |
| Visual evidence | Checkpoint screenshot, reviewed baseline/diff, DOM/ARIA snapshot, layout rectangles, console/page errors, network failures, and trace | Playwright traces retain action timing, DOM snapshots, console, network, and screenshot evidence; use tracing on failure or first retry ([Trace Viewer](https://playwright.dev/docs/trace-viewer); [Assertions](https://playwright.dev/docs/test-assertions)). |
| Responsiveness | `scrollWidth` vs `clientWidth`, text truncation, focus visibility, critical-control containment, and layout-shift observations across profiles | Separate true product overflow from the intentional two-dimensional play surface. |
| Responsiveness/performance | Observe LCP/INP where supported; collect long tasks and custom “ready for next action” marks | Use as trend signals until a controlled product baseline exists. LCP measures the largest visible content; INP covers click, tap, and keyboard interaction responsiveness ([Chrome/Web.dev LCP](https://web.dev/articles/optimize-lcp); [custom metrics and Event Timing](https://web.dev/articles/custom-metrics); [W3C Event Timing](https://www.w3.org/TR/event-timing/); [W3C Long Tasks](https://www.w3.org/TR/longtasks-1/)). |

## Interpretation limits

The robot can prove that a target is present, reachable, large enough, not obscured, and followed by understandable feedback. It cannot prove that users noticed the intended hierarchy, understood the game model, or felt low cognitive load. Those claims require moderated usability sessions, task success/error analysis with real players, and—if visual attention is a research question—eye-tracking or another validated attention method. The robot should therefore label screenshot-diff findings, geometry violations, and behavioral proxies separately from human-study findings.
